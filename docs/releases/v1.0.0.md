## Release Summary

Tsuzuru v1.0.0 is intended to stabilize the current web-first visual novel
engine foundation around the modern `.tzr` DSL.

This draft covers the release-note baseline only. It does not record an actual
publish event, version bump, git tag, GitHub release, npm provenance decision,
or post-publish registry result.

Target release version: `1.0.0`.

The current repository still contains pre-release package versions until an
approved release execution changes them. Package version values must not be
edited from this draft.

## Highlights

- Modern `.tzr` DSL v2 is the current scenario authoring path. The public parser
  and compiler APIs are `parseTzr` and `compileTzr` from `@tsuzuru/core`.
- `@tsuzuru/core` provides the browser-independent parser, compiler, project
  compiler, runtime IR, runtime stepping, choices, jumps, conditional branches,
  scenario state updates, plugin command dispatch, snapshots, and save-slot
  validation.
- Include-based multi-file scenario projects are supported through
  `include "./path.tzr"` and `compileTzrProject`.
- `@tsuzuru/cli` provides `tsuzuru check` for scenario validation through the
  configured project entry and scenario file set.
- `create-tsuzuru` provides the current project generator path for the basic
  Preact template.
- Preact and Vue adapters connect the core runtime to framework applications
  without moving scenario semantics out of core.
- `@tsuzuru/standard-ui-preact` provides reusable Preact visual novel UI
  components, including message, choice, viewport, and text reveal helpers.
- Official standard plugins cover visual, audio, text sound, effect, camera,
  particle, and system unlock state through runtime command handlers.
- Save/load validation is layered through `RuntimeSnapshot.version === 2`,
  `RuntimeSaveSlot.version === 1`, and adapter `RuntimeSaveData.version === 2`.
- Preact and Vue examples include RuntimeSaveSlot-based Save -> Load -> Restore
  coverage, with browser E2E available as an optional workflow.
- Release-readiness and publish-readiness gates check inventory, package
  artifacts, packed package contents, examples, and local `create-tsuzuru`
  smoke before an actual release is approved.

## Breaking Changes

For users coming from earlier experimental v0.x builds, v1.0 should be treated
as the stabilization point for the current DSL and runtime boundary.

- Legacy DSL syntax is not supported:
  - `#scene(...)`
  - `#label(...)`
  - `:: Speaker`
  - `@command(...)`
  - `$macro(...)`
  - legacy `@if` / `@else` / `@endif`
- Transitional parser/compiler names are not current APIs. Use `parseTzr` and
  `compileTzr`; do not use removed `parseTzrV2` or `compileTzrV2` aliases.
- Macro support, scenario-local macro definitions, preset syntax, stage syntax,
  and arbitrary JavaScript or TypeScript inside `.tzr` files are not part of
  v1.0.
- Parser-only or design-only syntax is not included in the v1.0 stable DSL
  subset. This includes rich inline text, inline waits/events, blank-line click
  waits, `---` page breaks, text block `:meta`, `system.*` condition reads,
  visual coordinate placement, and audio transition syntax.
- `@tsuzuru/core` remains independent from DOM, Preact, Vue, CSS, Vite,
  browser storage, and application asset loading. Hosts and framework adapters
  own presentation and storage policy.

## Migration Notes

- Replace old DSL syntax with the current DSL v2 syntax. Use the current docs
  and examples, especially `examples/preact-basic`, as the reference.
- Import parser/compiler APIs from `@tsuzuru/core` as `parseTzr`,
  `compileTzr`, and, for multi-file projects, `compileTzrProject`.
- Use `include "./path.tzr"` for multi-file scenario authoring. The include
  directive is compile-time only and does not become a runtime event.
- Register official standard plugin definitions when compiling scenarios that
  use standard plugin sugar or `call namespace.command(...)` validation.
- Do not rely on save data migration. v1.0 validates current save formats and
  rejects unsupported versions or mismatched scenario identity/version data.
- Scenario edits may invalidate existing save data because compiled instruction
  order, scene shape, runtime state, runtime events, and scenario version can
  change.
- `RuntimeSnapshot` and `RuntimeSaveSlot` validation rejects malformed, old,
  future, scenario-mismatched, and invalid nested snapshot payloads according to
  the current validation boundary.
- Plugin state migration is not guaranteed. Durable standard plugin state is
  preserved as runtime plugin state, while one-shot audio/effect events require
  the documented prepare helpers before creating save-ready snapshots.
- Generated projects should be regenerated or manually aligned when upgrading
  templates. `create-tsuzuru` templates are not a save-data or app-code
  migration framework.

## Known Limitations

- Tsuzuru v1.0 does not provide a save data migration framework for
  `RuntimeSnapshot`, `RuntimeSaveSlot`, adapter `RuntimeSaveData`, plugin state,
  scenario versions, host localStorage, IndexedDB, or remote storage.
- User-facing invalid save slot reason UI is minimal and example-level.
  Examples may filter invalid slots instead of showing detailed recovery
  reasons.
- Browser E2E remains optional. `pnpm examples:e2e` verifies Preact and Vue
  Save -> Load -> Restore flows, but it is not part of root `test` or
  `release-readiness:check`.
- Package graph validation remains optional/manual for v1.0. The experimental
  `packages:graph:check` is not the required distribution gate.
- Editor tooling, syntax highlighting, VS Code extension support, LSP
  diagnostics, and GUI editor support are not part of the v1.0 engine gate.
- Audio transitions such as `bgm ... with fadeIn(...)` and
  `stopBgm with fadeOut(...)` remain post-v1.0 design work.
- Visual coordinate placement such as `show asset at x=... y=...` remains
  post-v1.0 renderer coordinate policy work.
- Rich text, inline runtime events, inline audio events, blank-line click waits,
  page breaks, and text block metadata remain post-v1.0 text model work.
- `system.*` condition reads remain post-v1.0 resolver design work. The current
  std-system write side uses plugin commands such as
  `call system.unlockEnding(...)`.
- The final npm provenance, trusted publishing, manual publish, and two-factor
  authentication procedure remains an actual release-time maintainer decision.
