# v1.0 Standard Plugin Save/Load Matrix

## Purpose

This matrix records the v1.0 save/load policy for every official standard
plugin. It is a release-gate companion to
[`docs/architecture.md`](../architecture.md) and
[ADR 0031](../decisions/0031-v1-save-load-compatibility-promise.md).

The v1.0 promise is validation and rejection, not migration. Runtime snapshots
may preserve plugin state, but core does not deep-validate plugin state, migrate
plugin state, or automatically clear plugin-specific one-shot events.

## Policy Summary

- Durable plugin state remains in `RuntimeSnapshot` as normal runtime plugin
  state.
- One-shot plugin events must be cleared by a plugin helper or host prepare
  composition before creating a save-ready snapshot.
- Core does not automatically clear plugin one-shot state.
- Renderer, browser playback, asset resolution, animation timing, and storage
  are not runtime snapshot state.
- Plugin state migration is not part of the v1.0 compatibility promise.

## Coverage Inventory

- One-shot cleanup is covered by std-audio and std-effect integration tests.
- Durable keep-as-is state is covered by std-visual, std-text-sound,
  std-camera, std-particle, and std-system integration tests.
- Example save flows compose std-audio and std-effect prepare helpers before
  creating save-ready snapshots.
- Preact example E2E tests cover Save -> Load -> Restore through the host save
  slot envelope, but renderer output is intentionally not the source of plugin
  state truth.

## v1.0 Release Gate Conclusion

The standard plugin save/load matrix blocker is closed for v1.0. Every standard
plugin now has:

- documented durable / one-shot state classification
- an explicit snapshot preparation policy
- package-local state tests
- package-local save/load integration coverage for high-risk runtime state

The remaining plugin save/load work is post-v1.0 design work, especially plugin
state versioning and migration hooks. v1.0 does not promise plugin state
migration across future plugin state shape changes.

## Recommended Post-v1.0 Issue

### Design standard plugin state versioning and migration hooks

- Purpose: decide whether future standard plugin state changes need explicit
  per-plugin versioning or migration helpers.
- Scope: plugin state version metadata, migration entry points, validation
  responsibilities, host composition, docs, and compatibility tests.
- Done when: each standard plugin has either a documented no-migration policy
  or an explicit migration contract for future state shape changes.
- Suggested checks: `pnpm --filter @tsuzuru/core test`,
  `pnpm --filter @tsuzuru/plugin-std-audio test`,
  `pnpm --filter @tsuzuru/plugin-std-effect test`, `pnpm test`.
- Risk: premature migration promises can constrain runtime, plugin, adapter,
  and scenario evolution.
