# v0.7.0 Plan: Screen Runtime

## Status

Planned.

## Purpose

v0.7.0 adds screen DSL and runtime integration to Tsuzuru.

v0.6.0 added `ScreenHost` to `@tsuzuru/standard-ui-preact` as the custom screen UI foundation. In v0.6.0, screen state remained app-local and DSL / core runtime integration was intentionally deferred.

v0.7.0 connects the screen concept to core runtime and Preact adapter so that `.tzr` can open, close, and wait for custom screens.

The main implementation targets are:

- core screen commands
- runtime screen state
- runtime screen events
- screen close blocking
- `useRuntime` screen APIs
- `examples/standard-ui-preact` integration

v0.8.0 will revisit `create-tsuzuru` starter template integration.

## Planned DSL

```tzr
@openScreen("notebook")
@closeScreen()
@waitScreenClose()
```

### `@openScreen("screenId")`

`@openScreen` opens a custom screen by id.

Rules:

- The first positional argument is required.
- The first positional argument must be a non-empty string.
- Named arguments are not supported.
- Extra arguments are not supported.
- `screenId` is not validated against the app-local screen registry in core.
- Unknown screen ids are handled by `ScreenHost` fallback UI.
- `@openScreen` does not automatically block runtime progression.
- `@openScreen` sets `screen.active = { id: screenId }`.
- If another screen is already open, `@openScreen` overwrites it.
- `@openScreen` does not change `screen.waitingForClose`.

Valid:

```tzr
@openScreen("notebook")
```

Invalid:

```tzr
@openScreen("")
@openScreen("notebook", "extra")
@openScreen(screenId="notebook")
```

### `@closeScreen()`

`@closeScreen` closes the current screen.

Rules:

- No arguments are allowed.
- Bare form is not allowed.
- If no screen is active, it is a no-op.
- It sets `screen.active = null`.
- It sets `screen.waitingForClose = false`.

Valid:

```tzr
@closeScreen()
```

Invalid:

```tzr
@closeScreen
@closeScreen("notebook")
```

### `@waitScreenClose()`

`@waitScreenClose` waits until the active screen is closed.

Rules:

- No arguments are allowed.
- Bare form is not allowed.
- If no screen is active, it is a no-op.
- If a screen is active, it sets `screen.waitingForClose = true`.
- Runtime progression is blocked while `screen.waitingForClose` is true.
- When `screen.active === null`, `screen.waitingForClose` becomes false.
- `waitScreenClose` is not exposed as a runtime API from `useRuntime`.
- `waitScreenClose` is DSL-only in v0.7.0.

Valid:

```tzr
@waitScreenClose()
```

Invalid:

```tzr
@waitScreenClose
@waitScreenClose("notebook")
```

## Important Design Policy

`@openScreen("id")` is not blocking by default.

This is intentional. Opening a screen and waiting for the screen to close are separate operations.

```txt
open:
  display the screen

close:
  clear the screen

wait:
  block runtime progression until the screen is closed
```

This allows tutorial-style presentation where a screen remains visible while the message window continues explaining it.

```tzr
:: System
手帳を確認してみましょう。

@openScreen("notebook")

:: System
証拠が集まれば、ここに追記されます。

@closeScreen()
```

If the story should wait until the user closes the screen, use `@waitScreenClose()` explicitly.

```tzr
:: System
手帳を確認してください。

@openScreen("notebook")
@waitScreenClose()

:: System
確認できましたね。
```

## Planned Runtime State

Add screen state to `RuntimeState`.

```ts
export type RuntimeActiveScreen = {
  readonly id: string;
};

export type RuntimeScreenState = {
  readonly active: RuntimeActiveScreen | null;
  readonly waitingForClose: boolean;
};

export type RuntimeState = {
  // existing fields...
  readonly screen: RuntimeScreenState;
};
```

Initial state:

```ts
screen: {
  active: null,
  waitingForClose: false,
}
```

### State Transitions

`@openScreen("notebook")`:

```ts
screen: {
  active: { id: "notebook" },
  waitingForClose: currentWaitingForClose,
}
```

`@closeScreen()`:

```ts
screen: {
  active: null,
  waitingForClose: false,
}
```

`@waitScreenClose()` when screen is active:

```ts
screen: {
  active: currentActiveScreen,
  waitingForClose: true,
}
```

`@waitScreenClose()` when screen is not active:

```ts
screen: {
  active: null,
  waitingForClose: false,
}
```

## Planned Runtime Event

Add `ScreenRuntimeEvent`.

```ts
export type ScreenRuntimeEvent = {
  readonly type: "screen";
  readonly action: "open" | "close" | "waitClose";
  readonly screenId?: string;
};
```

Event examples:

```ts
{ type: "screen", action: "open", screenId: "notebook" }
{ type: "screen", action: "close" }
{ type: "screen", action: "waitClose" }
```

`screen` runtime events are transient and non-renderable.

They should not be displayed by `RuntimeMessageLayer`.

They should be auto-steppable in `useRuntime`.

## Planned Runtime Block Reason

Add `"screenClose"` to `RuntimeBlockReason`.

```ts
export type RuntimeBlockReason =
  | "wait"
  | "choice"
  | "click"
  | "screenClose";
```

`screenClose` has the highest priority.

```ts
export function getRuntimeBlockReason(state: RuntimeState): RuntimeBlockReason | null {
  if (state.screen.waitingForClose) {
    return "screenClose";
  }
  if (state.pendingWait !== null) {
    return "wait";
  }
  if (state.pendingChoice !== null) {
    return "choice";
  }
  if (state.isWaitingForClick) {
    return "click";
  }
  return null;
}
```

## Planned Runtime Behavior

### `stepRuntime()` while waiting for screen close

`stepRuntime()` should stop in core while `screen.waitingForClose` is true.

```ts
if (state.screen.waitingForClose) {
  return {
    state,
    event: { type: "screen", action: "waitClose" },
  };
}
```

This mirrors existing core-level blocking behavior for pending wait, pending choice, and click wait.

### Clearing screen close wait

When `screen.active === null`, `screen.waitingForClose` must become false.

This applies regardless of how the screen is closed:

- `@closeScreen()`
- `runtime.closeScreen()`
- `ScreenHost.onClose`

## Planned Runtime API

Add runtime helper APIs for app / adapter integration.

Preferred public helpers:

```ts
openScreen(state: RuntimeState, screenId: string): RuntimeState;
closeScreen(state: RuntimeState): RuntimeState;
```

Exact file placement can be adjusted to match existing runtime organization.

`useRuntime` should expose:

```ts
runtime.openScreen("notebook");
runtime.closeScreen();
```

`useRuntime` should not expose:

```ts
runtime.waitScreenClose();
```

`waitScreenClose` remains DSL-only in v0.7.0.

## Snapshot / Save Policy

In v0.7.0, screen state is transient.

```txt
save:
  screen.active is not preserved
  screen.waitingForClose is not preserved

restore:
  screen.active = null
  screen.waitingForClose = false
```

`RuntimeSnapshot` and `RuntimeSaveData` should not restore active screen state.

On restore:

```ts
screen: {
  active: null,
  waitingForClose: false,
}
```

## ScreenHost Compatibility

v0.6.0 `ScreenHost` keeps its params-capable `ActiveScreen` type.

```ts
export type ActiveScreen<TParams = unknown> = {
  readonly id: string;
  readonly params?: TParams;
};
```

Core runtime state uses params-free active screen in v0.7.0.

```ts
export type RuntimeActiveScreen = {
  readonly id: string;
};
```

A core active screen can be passed to `ScreenHost`.

```tsx
<ScreenHost
  activeScreen={runtime.state.screen.active}
  screens={screens}
  onClose={runtime.closeScreen}
/>
```

## Acceptance Criteria

- `@openScreen("screenId")` is available as a core command.
- `@closeScreen()` is available as a core command.
- `@waitScreenClose()` is available as a core command.
- `@openScreen` uses positional screen id only.
- `@openScreen("")` is validation error.
- `@openScreen("id", extra)` is validation error.
- `@openScreen(screenId="id")` is validation error.
- `@closeScreen("id")` is validation error.
- `@waitScreenClose("id")` is validation error.
- Bare `@closeScreen` is not accepted.
- Bare `@waitScreenClose` is not accepted.
- `runtimeState.screen.active` is updated by `@openScreen`.
- `runtimeState.screen.active` is cleared by `@closeScreen`.
- `runtimeState.screen.waitingForClose` is set by `@waitScreenClose` when screen is active.
- `@waitScreenClose()` is no-op when no screen is active.
- `@closeScreen()` is no-op when no screen is active.
- `@openScreen` does not automatically block runtime progression.
- `@waitScreenClose` blocks runtime progression until screen is closed.
- `screenClose` is returned as block reason.
- `screenClose` has highest block priority.
- `ScreenRuntimeEvent` is non-renderable.
- `ScreenRuntimeEvent` is auto-steppable.
- runtime API exposes `openScreen` / `closeScreen`.
- `useRuntime` exposes `openScreen` / `closeScreen`.
- `useRuntime` does not expose `waitScreenClose`.
- screen state is not restored from snapshot / save data.
- `examples/standard-ui-preact` uses runtime screen state with `ScreenHost`.
- example scenario demonstrates `open → wait → UI close → resume`.
- example scenario demonstrates `open → message → close`.
- params are not implemented.
- screen stack is not implemented.
- screen mode is not implemented.
- create-tsuzuru is not changed.
