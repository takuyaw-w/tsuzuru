# v1.0 Release Gate

## Purpose

This plan defines the release gate shape for Tsuzuru v1.0. It separates checks
that are already automated from optional browser checks, manual release steps,
and design readiness items that still need product or compatibility decisions.

The goal is not to run a release from this document. Do not publish packages,
create git tags, create GitHub releases, or bump versions as part of this plan.

## Current Status

Tsuzuru now has strong repository-level infrastructure:

- package inventory and script coverage checks
- publish-readiness checks for package tarball contents
- release-readiness checks for package builds, examples, pack dry-run,
  publish-readiness, and local `create-tsuzuru` smoke
- TypeScript package graph validation through `packages:graph:check`
- runtime snapshot and save slot compatibility policies
- v1.0 save/load compatibility promise through ADR 0031
- std plugin save/load regression coverage for audio and effect one-shot state
- Preact and Vue example save/load storage tests
- Preact and Vue Save -> Load -> Restore Playwright E2E smoke
- optional GitHub Actions workflow for browser E2E

The current status is a strong pre-v1.0 foundation, not a v1.0 release approval.
Several plugin-matrix, package-graph, and manual release-policy decisions still
need to be closed before v1.0.

## Required Gates

These are the required local and CI gates for the current release-readiness
model:

```sh
pnpm inventory:check
pnpm format:check
pnpm lint
pnpm check
pnpm test
pnpm typecheck
pnpm packages:build
pnpm publish-readiness:check
pnpm release-readiness:check
git diff --check
```

CI maps these through:

- `quality-fast`: inventory, formatting, lint, Biome check, tests, typecheck,
  and whitespace diff check
- `quality-release-readiness`: `pnpm release-readiness:check`

`release-readiness:check` currently runs:

```txt
packages:build
examples:check:self
pack:dry-run
publish-readiness:check
smoke:create-tsuzuru:local
```

This is the distribution gate. It must remain focused on package artifacts,
example build viability, tarball contents, publish readiness, and generated
project smoke.

## Optional Gates

Browser E2E remains optional for now:

```sh
pnpm examples:e2e
```

`examples:e2e` runs Playwright Save -> Load -> Restore smoke tests for
`examples/preact-basic` and `examples/vue-basic`, including RuntimeSaveSlot
browser storage paths.

GitHub Actions exposes this through the optional `Examples E2E` workflow:

- manual trigger: `workflow_dispatch`
- scheduled trigger: nightly UTC schedule
- not a `push` or `pull_request` gate
- not part of root `test`
- not part of `release-readiness:check`

This stays optional because Playwright checks are heavier and more sensitive to
browser, asset, and dev-server environment changes than package and unit gates.
Promoting this to a required PR gate should be a separate decision after a
stability observation period.

## Manual Gates

These steps remain manual and must not be hidden inside automated scripts
without a separate release-process decision:

- confirm npm login and organization/package permissions
- decide whether npm provenance is required for v1.0
- run any chosen `pnpm publish --dry-run` manifest conversion checks
- review generated tarball contents for public package layout
- prepare release notes
- create the version bump commit
- create and push the git tag
- create the GitHub release
- publish packages in dependency order
- run registry-backed `smoke:create-tsuzuru:registry` after publish

`release:version` performs version edits, verification, commit, tag, and push.
It must only be run intentionally during release execution, not as a readiness
check.

## Design Readiness Gates

The following design gates should be explicit before v1.0 is considered stable.

### DSL support matrix

Current status:

- [`docs/design/dsl-support-matrix.md`](../design/dsl-support-matrix.md) lists
  current `.tzr` syntax by parser, compiler, runtime/plugin, docs, examples,
  tests, and v1.0 status.
- Core DSL and official standard plugin sugar are separated.
- Removed legacy DSL syntax is tracked as `removed-legacy`, not current syntax.
- Parser-only text features are explicitly out of the v1.0 stable subset:
  rich inline text, inline waits/events, blank-line click waits, page breaks,
  and `:meta` remain post-v1.0 design work.
- `system.*` conditions are explicitly out of the v1.0 stable subset.
  std-system write-side `call system.unlock...` commands remain
  plugin-dependent.
- Visual coordinate placement is explicitly out of the v1.0 stable subset.
  std-visual preset placement (`left` / `center` / `right`) remains
  plugin-dependent.
- Audio transition syntax is explicitly out of the v1.0 stable subset.
  statement-level std-audio commands (`bgm`, `stopBgm`, `se`, `voice`) remain
  plugin-dependent.
- Editor tooling such as syntax highlighting, VS Code extension support, LSP
  diagnostics, and GUI editor support is explicitly not a v1.0 blocker. It
  remains optional tooling that can ship independently after engine v1.0.

The DSL support-scope blocker is closed for v1.0. Future editor tooling should
follow the support matrix instead of defining a separate supported syntax.

### Save/load compatibility

Already covered:

- `RuntimeSnapshot.version === 2` restore validation
- malformed, old, and future snapshot rejection
- `RuntimeSaveSlot.version === 1` envelope validation
- scenario ID and scenario version mismatch rejection
- adapter `RuntimeSaveData` helpers for Preact and Vue
- std-audio and std-effect one-shot cleanup regression
- example invalid slot filtering and browser Save -> Load -> Restore smoke
- ADR 0031 defines the v1.0 promise as validation / rejection, not migration

The save/load compatibility blocker is closed for v1.0. v1.0 guarantees current
format validation and mismatch rejection for `RuntimeSnapshot`,
`RuntimeSaveSlot`, and adapter `RuntimeSaveData`. It does not guarantee
RuntimeSnapshot migration, RuntimeSaveSlot migration, plugin state migration,
scenario version migration, host storage migration, or compatibility after
arbitrary scenario/runtime/event shape changes.

User-facing invalid save slot reason UI remains a non-blocking improvement.

### Standard plugin matrix

Already covered by package tests and architecture docs:

- std-visual durable background/sprite state
- std-audio durable BGM plus one-shot SE/voice cleanup helper
- std-effect one-shot events cleanup helper
- std-camera durable camera state
- std-particle durable particle state
- std-system durable unlock state
- std-text-sound durable override state and browser helper separation

Still needed before v1.0:

- issue-ready matrix confirming durable vs one-shot state for every std plugin
- integration-style save/load tests for durable plugins where the risk is high
- explicit docs for plugins whose state should be kept as-is in snapshots

### Package graph

Already covered:

- `packages:graph:check` validates the current TypeScript project reference
  pilot graph with `tsc -b --dry --verbose`
- `build:self` remains artifact generation
- `release-readiness:check` remains distribution validation

Still needed before v1.0:

- decide whether a formal `tsconfig.packages.json` is required for v1.0
- if required, complete project references for the publishable package graph
- keep `tsc -b` scoped as graph validation unless a separate artifact-build
  migration is explicitly designed

### Publish strategy

Already covered:

- package builds
- pack dry-run
- publish-readiness tarball inspection
- local create-tsuzuru smoke

Still needed before v1.0:

- publish order and exact command checklist
- npm provenance decision
- registry publish dry-run policy
- post-publish registry smoke requirement
- release notes template

## Already Covered

- Required CI split exists: `quality-fast` and `quality-release-readiness`.
- Optional E2E workflow exists and is not required for PRs.
- Root `test` and `release-readiness:check` do not call browser E2E.
- `publish-readiness:check` validates public package file lists and exports.
- `release-readiness:check` validates package artifacts and generated project
  smoke through local tarballs.
- Runtime snapshot, save slot, adapter save data, and v1.0 compatibility
  boundaries are recorded in ADR 0028, ADR 0029, ADR 0030, and ADR 0031.
- Preact and Vue examples use RuntimeSaveSlot-based save data and have unit plus
  browser smoke coverage.

## Missing / Weak Areas

- DSL support matrix now exists and the v1.0 DSL support-scope decisions are
  closed. Parser-only text features, `system.*` conditions, visual coordinate
  placement, and audio transitions are scoped out of the v1.0 stable subset.
  Editor tooling is optional and non-blocking.
- Save/load migration is not implemented by design; ADR 0031 makes migration a
  non-goal for the v1.0 compatibility promise.
- Invalid save slot UI is limited to filtering; detailed reason display is not
  implemented.
- Standard plugin save/load integration coverage is strongest for audio/effect;
  durable plugin integration coverage can still be improved.
- `packages:graph:check` is still pilot-only and not a complete package graph.
- Manual publish, provenance, tag, and GitHub release procedures are not yet a
  v1.0-ready checklist.
- VS Code extension / syntax highlighting remains post-v1.0 optional tooling,
  not a release blocker.

## Release Blockers

These should block v1.0 until resolved:

1. Manual npm publish strategy, provenance decision, tag strategy, and release
   notes procedure are not complete.
2. Standard plugin state matrix is not fully converted into issue-ready
   verification tasks.
3. Formal package graph status is undecided: either explicitly non-blocking for
   v1.0 or completed as a validation gate.

## Non-blocking Improvements

These improve confidence but should not automatically block v1.0 unless scoped
as release requirements:

- promote `examples:e2e` to a PR optional or required check after observation
- add invalid save slot reason display to example UIs
- add more browser visual regression assertions
- add Vue standard UI package design
- add syntax highlighting package or VS Code extension
- add formal save data migration framework

## Recommended Next Tasks

The following tasks are written at GitHub issue granularity. The first group
records DSL follow-up work that was scoped out of v1.0 or made optional; the
later tasks cover remaining release blockers and process gaps.

## Recommended Issues

### 1. Track editor and syntax highlighting support after v1.0

- Purpose: improve `.tzr` authoring UX without making engine v1.0 depend on
  editor tooling.
- Scope: syntax grammar, VS Code extension decision, optional LSP diagnostics,
  snippets, docs, release cadence, and support-matrix alignment.
- Done when: editor tooling has an implementation plan or separate release
  vehicle, and docs explain how its grammar follows the v1.0 DSL subset.
- Suggested checks: docs-only `pnpm check`; future grammar checks when tooling
  exists.
- Risk: editor grammar can drift from parser/compiler behavior if it is not
  validated against the support matrix.

### 2. Design rich text and inline event support after v1.0

- Purpose: keep v1.0 text authoring stable while preserving a path for richer
  message-window behavior later.
- Scope: renderer message model, text reveal timing, backlog representation,
  save/load interaction, inline audio events, `:meta`, blank-line click waits,
  `---` page breaks, `{text}`, `{delay}`, `{wait}`, inline `{se}`, and inline
  `{voice}`.
- Done when: each parser-only text feature has a compiler/runtime design,
  renderer contract, compatibility notes, tests, and user docs before being
  promoted from parser-only.
- Suggested checks: `pnpm --filter @tsuzuru/core test`, `pnpm check`,
  `pnpm test`.
- Risk: rich text and inline events affect renderer, message history, backlog,
  skip/auto behavior, and save/load compatibility.

### 3. Design visual coordinate placement after v1.0

- Purpose: allow arbitrary sprite coordinates later without locking the v1.0
  renderer coordinate model.
- Scope: coordinate origin, units, anchors, safe area, responsive layout,
  std-visual state shape, compiler support, docs, and examples.
- Done when: `show asset at x=... y=...` has a renderer contract, compiler and
  plugin state design, tests, and user docs before being promoted from
  parser-only.
- Suggested checks: `pnpm --filter @tsuzuru/core test`,
  `pnpm --filter @tsuzuru/plugin-std-visual test`, `pnpm check`.
- Risk: coordinate placement can constrain renderer layout and save/load state
  shape if stabilized too early.

### 4. Design audio transitions after v1.0

- Purpose: add BGM fade behavior later without locking host audio timing or
  transition save/load semantics in v1.0.
- Scope: `bgm ... with fadeIn(...)`, `stopBgm with fadeOut(...)`, possible
  SE/Voice transition policy, std-audio state or event shape, renderer timing,
  transition-in-progress save/load behavior, docs, and examples.
- Done when: audio transitions have an explicit audio-layer contract,
  save/load policy, compiler/plugin design, tests, and user docs before being
  promoted from design-only.
- Suggested checks: `pnpm --filter @tsuzuru/core test`,
  `pnpm --filter @tsuzuru/plugin-std-audio test`, `pnpm check`.
- Risk: transition timing and in-progress restore behavior can constrain host
  audio implementations too early.

### 5. Design save/load migration and invalid-slot UI after v1.0

- Purpose: design migration and user-facing restore failure UX without expanding
  the v1.0 promise beyond validation / rejection.
- Scope: RuntimeSnapshot migration, RuntimeSaveSlot migration, adapter
  RuntimeSaveData migration, plugin state migration, scenario version migration,
  host storage migration, invalid slot reason display, and recovery copy.
- Done when: a post-v1.0 design says which migration layers are supported and
  how hosts expose invalid save reasons.
- Suggested checks: `pnpm --filter @tsuzuru/core test`,
  `pnpm --filter @tsuzuru/example-preact-basic test`,
  `pnpm --filter @tsuzuru/example-vue-basic test`.
- Risk: migration promises can constrain runtime, plugin, adapter, and scenario
  evolution if they are added without a versioned framework.

### 6. Design `system.*` condition resolver after v1.0

- Purpose: allow scenarios to branch on std-system durable unlock state without
  making core own plugin persistence semantics.
- Scope: renderer-neutral resolver contract, runtime condition evaluator
  boundary, std-system state shape, save/load compatibility, docs, and examples.
- Done when: `if system.*` and conditional choices using `system.*` have an
  explicit resolver design, tests, and user docs before being promoted from
  parser-only.
- Suggested checks: `pnpm --filter @tsuzuru/core test`,
  `pnpm --filter @tsuzuru/plugin-std-system test`, `pnpm check`.
- Risk: system unlock state crosses runtime snapshots, app persistence,
  galleries, achievements, and plugin-owned state boundaries.

### 7. Complete the standard plugin save/load matrix

- Purpose: ensure every std plugin has a durable/one-shot save policy and
  appropriate regression coverage.
- Scope: audit std-visual, audio, effect, camera, particle, system, and
  text-sound; add integration tests where state risk justifies it.
- Done when: each plugin has documented snapshot behavior and high-risk state
  has tests.
- Suggested checks: `pnpm --filter @tsuzuru/plugin-std-audio test`,
  `pnpm --filter @tsuzuru/plugin-std-effect test`, `pnpm test`.
- Risk: adding tests across many plugins can uncover ambiguous plugin-state
  semantics.

### 8. Write the v1.0 manual publish checklist

- Purpose: remove ambiguity from final release execution.
- Scope: npm login/whoami, provenance decision, publish dry-run, package order,
  tag creation, GitHub release notes, post-publish registry smoke.
- Done when: a maintainer can execute the release without inferring order from
  historical v0.1 docs.
- Suggested checks: docs-only `pnpm check`, plus dry-run commands only when
  explicitly approved.
- Risk: confusing dry-run and actual publish steps can lead to accidental
  release actions.

### 9. Decide whether the package graph is a v1.0 gate

- Purpose: decide whether `packages:graph:check` remains optional validation or
  becomes part of v1.0 readiness.
- Scope: evaluate remaining package reference edges and formal
  `tsconfig.packages.json` requirements.
- Done when: v1.0 docs state either "not blocking" or define the exact formal
  graph gate.
- Suggested checks: `pnpm packages:graph:check`, `pnpm packages:build`,
  `pnpm publish-readiness:check`.
- Risk: treating `tsc -b` as artifact build would conflict with current
  package layout and non-TypeScript build steps.

## Decision Notes

- `examples:e2e` stays optional until its browser/dev-server stability is
  observed over time.
- `packages:graph:check` is dependency graph validation, not artifact build.
- `release-readiness:check` remains the distribution gate and does not call
  `examples:e2e` or `packages:graph:check`.
- ADR 0031 defines the v1.0 save/load promise as validation / rejection, not
  migration.
- v1.0 should not imply compatibility with legacy DSL syntax.
- v1.0 text authoring should imply plain narration/dialogue text only;
  parser-only rich text and inline event features remain post-v1.0.
- v1.0 condition authoring should imply `scenario.*` references only;
  `system.*` condition resolver design remains post-v1.0.
- v1.0 visual placement should imply preset std-visual placement only;
  coordinate placement remains post-v1.0 renderer policy work.
- v1.0 audio authoring should imply statement-level std-audio commands only;
  audio transitions remain post-v1.0 audio-layer and save/load design work.
- Editor tooling, syntax highlighting, VS Code extension support, LSP
  diagnostics, and GUI editor support are recommended future tooling, not v1.0
  release blockers.
