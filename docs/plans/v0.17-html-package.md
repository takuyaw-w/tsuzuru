# v0.17 HTML Package Plan

Status: reverted / superseded.

This plan is historical. The experimental framework-free HTML route was removed:
`packages/html`, `examples/html-basic`, and
`packages/create-tsuzuru/templates/html` no longer exist. `@tsuzuru/html` is not
a current package, and `create-tsuzuru --template html` is not supported.
Current official v0.x UI work is focused on Preact-based JSX.

This plan prepares a future `@tsuzuru/html` package and `examples/html-basic`
example for Tsuzuru users who want Vanilla DOM / HTML instead of Preact.

The design decision is recorded in `docs/decisions/0021-html-package.md`.

## Goals

- Add a future package named `@tsuzuru/html`.
- Use `packages/html` as the package directory.
- Do not name the package `web-player`.
- Keep `@tsuzuru/html` free of Preact, React, Vue, and other UI framework
  dependencies.
- Provide a Vanilla DOM / HTML runtime + UI adapter.
- Add a future `examples/html-basic` example that demonstrates Tsuzuru without
  Preact.
- Preserve existing `@tsuzuru/preact` and `@tsuzuru/standard-ui-preact`
  responsibilities.
- Keep core runtime, DSL, and plugin semantics unchanged.

## Non-Goals

This plan does not implement the package.

Out of scope for this planning task:

- creating `packages/html`
- creating `examples/html-basic`
- changing public APIs
- changing package versions
- editing `package.json` files
- editing `pnpm-workspace.yaml`
- changing `.tzr` syntax
- changing core runtime behavior
- changing std-visual or std-audio plugin behavior
- changing `create-tsuzuru` behavior now
- git push, git tag, npm publish, or release work

## Existing Context

`@tsuzuru/core` already provides the required engine primitives:

- `compileTzrProject({ entryId, documents }, options)`
- `createInitialRuntimeState`
- `stepRuntime`
- `resolveChoice`
- wait clearing
- snapshots and restore
- runtime diagnostics
- plugin command dispatch

`@tsuzuru/preact` wraps those primitives in Preact hooks and helpers. Its
important adapter behaviors are:

- visible runtime event filtering
- auto-clearing wait events
- auto-stepping transient events
- choice selection wiring
- save data helpers that retain the current visible event

`@tsuzuru/standard-ui-preact` provides Preact UI components and Preact hooks:

- `GameShell`
- `GameViewport`
- `MessageWindow`
- `ChoiceLayer`
- `StatusLayer`
- `RuntimeMessageLayer`
- `useAutoMode`
- `useMessageHistory`
- `useTextReveal`

`@tsuzuru/plugin-std-visual` and `@tsuzuru/plugin-std-audio` intentionally store
renderer-neutral state. They do not resolve asset paths, create DOM nodes, or
load media.

`examples/preact-basic` currently demonstrates the full Preact path. It compiles
multi-file scenarios with Vite `import.meta.glob`, drives runtime with
`@tsuzuru/preact`, renders Preact UI, and keeps visual/audio/browser storage
policy in the example.

`create-tsuzuru` defaults to the bundled Preact-based `basic` template and also
supports `--template html` for the framework-free HTML template.

## Adopted Package Shape

`@tsuzuru/html` should be a single package that combines:

- a DOM runtime controller
- a minimal standard DOM UI
- scenario URL loading helpers
- optional asset manifest loading
- default std-visual DOM rendering
- default std-audio browser playback
- exported CSS

This differs from the Preact split where `@tsuzuru/preact` and
`@tsuzuru/standard-ui-preact` are separate. The split remains correct for Preact
because Preact users compose hooks and components. For Vanilla DOM users, a
single imperative mount API is the simpler first entry point.

The package may later be split if the DOM UI grows enough to justify a separate
`@tsuzuru/standard-ui-html` package.

## Responsibility Model

### `@tsuzuru/html` owns

- `mountTsuzuruHtml(root, options)`
- DOM node creation and update lifecycle
- root shell, message window, choice layer, status layer, visual layer, and
  audio layer DOM rendering
- default title/start flow for URL-loaded scenarios
- browser event wiring for click-to-advance and choice buttons
- runtime controller state around core `RuntimeState`
- visible event tracking
- transient event auto-step scheduling
- wait auto-clear scheduling
- basic save data helpers equivalent in shape to the Preact adapter approach
- scenario URL fetching when the host requests it
- recursive include fetching for URL-loaded scenarios
- asset manifest fetching and validation at the adapter level
- browser image and audio element management
- CSS class names and CSS variable defaults

### `@tsuzuru/html` does not own

- parser behavior
- compiler validation
- runtime stepping semantics
- choice resolution semantics
- condition semantics
- standard plugin command schemas
- plugin-owned state shape
- persistent save storage policy
- project scaffolding policy
- package versioning
- asset ID compiler validation

## Boundary with `@tsuzuru/preact`

`@tsuzuru/preact` remains the Preact adapter. It should not depend on
`@tsuzuru/html`, and `@tsuzuru/html` should not depend on `@tsuzuru/preact`.

Conceptual overlap is allowed:

- both packages can filter visible events
- both packages can auto-clear waits
- both packages can auto-step transient events
- both packages can provide save data helpers

Implementation sharing should not be forced until there is a clearly framework-
neutral helper worth extracting. If duplication becomes risky, extract pure
helpers to a future package or to core only when the helper is not DOM,
Preact, storage, or UI policy.

## Boundary with `@tsuzuru/standard-ui-preact`

`@tsuzuru/standard-ui-preact` remains Preact-only.

`@tsuzuru/html` should not import its components, CSS, or hooks. The HTML
package may use similar class naming concepts and UX conventions, but the DOM
implementation must be independent.

`@tsuzuru/standard-ui-preact` should not gain DOM mounting APIs for this work.

## Initial Public API Proposal

### `mountTsuzuruHtml`

Primary entry point:

```ts
import { mountTsuzuruHtml } from "@tsuzuru/html";
import "@tsuzuru/html/style.css";

const player = await mountTsuzuruHtml(document.getElementById("app")!, {
  scenario: {
    entryUrl: "/scenario/main.tzr",
    entryId: "public/scenario/main.tzr",
  },
  assetsUrl: "/assets/assets.json",
});
```

The function should:

1. Clear or claim the root.
2. Load and compile the scenario source when needed.
3. Load assets when `assetsUrl` is provided.
4. Create runtime state with plugins.
5. Render the initial title or runtime state.
6. Return an imperative player handle.

Candidate handle:

```ts
export interface TsuzuruHtmlPlayer {
  readonly root: HTMLElement;
  readonly ready: Promise<void>;
  readonly start: () => void;
  readonly step: () => void;
  readonly choose: (itemIndex: number) => void;
  readonly reset: () => void;
  readonly destroy: () => void;
  readonly createSnapshot: () => RuntimeSnapshot;
  readonly restoreSnapshot: (snapshot: RuntimeSnapshot) => void;
  readonly createSaveData: () => RuntimeSaveData;
  readonly restoreSaveData: (saveData: RuntimeSaveData) => void;
  readonly getState: () => RuntimeState;
  readonly getEvent: () => RuntimeEvent | null;
  readonly getVisibleEvent: () => RuntimeEvent | null;
}
```

### Scenario Inputs

Support three source modes:

```ts
type TsuzuruHtmlScenarioSource =
  | { readonly document: RuntimeDocument }
  | { readonly entryId: string; readonly documents: readonly TzrProjectDocumentInput[] }
  | { readonly entryUrl: string | URL; readonly entryId?: string };
```

The compiled document mode is for hosts that compile elsewhere.

The project document mode is for bundlers or hosts that already loaded all
files.

The URL mode is for plain static hosting and `examples/html-basic`.

### Runtime Options

Candidate mount options:

```ts
export interface MountTsuzuruHtmlOptions {
  readonly scenario: TsuzuruHtmlScenarioSource;
  readonly assets?: TsuzuruHtmlAssets;
  readonly assetsUrl?: string | URL;
  readonly plugins?: readonly RuntimePluginDefinition[];
  readonly commandHandlers?: Readonly<Record<string, RuntimePluginCommandHandler>>;
  readonly autoStart?: boolean;
  readonly autoClearWait?: boolean;
  readonly autoStepTransientEvents?: boolean;
  readonly autoStepMaxSteps?: number;
  readonly onDiagnostic?: (diagnostic: TsuzuruHtmlDiagnostic) => void;
  readonly fetch?: typeof globalThis.fetch;
}
```

Defaults:

- `autoStart: false`, so the default title/start screen is visible first.
- `autoClearWait: true`, matching the current example behavior.
- `autoStepTransientEvents: true`, so scene/state/jump/plugin events do not
  appear as debug UI.
- std-visual and std-audio plugins and handlers are registered by default.

Hosts can pass custom plugins/handlers to replace or extend the defaults.

## Scenario URL Loading Policy

URL loading exists only in `@tsuzuru/html`. It does not change core.

For `entryUrl`:

- fetch the entry as UTF-8 text
- derive `entryId` from `entryId` option or from the URL pathname
- parse the entry to discover include directives
- recursively fetch included files
- compile all loaded documents with `compileTzrProject`

Diagnostics:

- network failure: adapter diagnostic
- non-OK response: adapter diagnostic
- parse/compile failure: core diagnostics passed through
- missing include: adapter diagnostic if fetch fails, then compile diagnostic
  if document is absent

The loader should use an injectable `fetch` for tests.

## Include-Based Multi-File Resolution

The loader must mirror accepted include behavior:

- only top-level `include "./path.tzr"` directives are followed
- paths resolve relative to the including document id
- duplicate includes are deduplicated
- circular includes are diagnosed
- no runtime event is emitted for include directives

The loader tracks:

- `document.id` for core compile diagnostics and save pointer file paths
- `document.url` for browser fetch resolution

Example:

```txt
entryUrl: /scenario/main.tzr
entryId: public/scenario/main.tzr
include "./chapters/01-opening.tzr"
```

resolves to:

```txt
fetch URL: /scenario/chapters/01-opening.tzr
document id: public/scenario/chapters/01-opening.tzr
```

The browser loader must not implement glob scanning. Directory scanning remains
a CLI concern through `tsuzuru.config.ts`.

## assets.json Design

Initial asset manifest:

```json
{
  "version": 1,
  "baseUrl": "./",
  "visual": {
    "backgrounds": {
      "station": { "src": "images/backgrounds/station.webp", "alt": "Station" }
    },
    "sprites": {
      "mio_smile": { "src": "images/sprites/mio-smile.webp", "alt": "美緒" }
    }
  },
  "audio": {
    "bgm": {
      "daily_theme": { "src": "audio/bgm/daily-theme.ogg" }
    },
    "se": {
      "page": { "src": "audio/se/page.wav" }
    },
    "voice": {
      "mio_001": { "src": "audio/voice/mio-001.ogg" }
    }
  }
}
```

Rules:

- `version` is required and initially must be `1`.
- `baseUrl` is optional and resolves relative to the manifest URL.
- each `src` resolves relative to `baseUrl` if present, otherwise the manifest
  URL.
- missing visual assets render a non-fatal placeholder and diagnostic.
- missing audio assets emit a non-fatal diagnostic and skip playback.
- unsupported manifest versions are mount diagnostics.

Deferred:

- compiler validation against `assets.json`
- multiple source formats per asset
- preloading policy
- image dimensions as layout contracts
- sprite pivots
- audio volume/fade/channel metadata

## std-visual Handling

Default std-visual integration should:

- register `createStdVisualPlugin()`
- pass `createStdVisualCommandHandlers()`
- read `getStdVisualState(runtimeState)` after runtime changes
- render one background layer
- render sprite elements keyed by asset ID
- map `left`, `center`, and `right` to CSS classes
- apply transition metadata through CSS classes and `--tzr-html-transition-ms`
- treat missing assets as non-fatal

The package should not add new std-visual commands or change std-visual state.

## std-audio Handling

Default std-audio integration should:

- register `createStdAudioPlugin()`
- pass `createStdAudioCommandHandlers()`
- read `getStdAudioState(runtimeState)` after runtime changes
- keep one managed BGM audio element
- consume SE events by sequence
- consume Voice events by sequence
- stop previous voice playback by default for the first implementation
- report missing files and autoplay failures as non-fatal diagnostics

The package should not change std-audio state or add playback policy to the
plugin package.

Save/load should use `prepareStdAudioStateForSnapshot(runtimeState)` before
creating snapshots when std-audio is active, matching existing std-audio save
policy.

## CSS Customization

Export:

```txt
@tsuzuru/html/style.css
```

CSS expectations:

- root classes use a `tzr-html-` prefix
- no Shadow DOM by default
- default CSS is usable but intentionally plain
- host projects can override with ordinary CSS after importing the package CSS
- CSS variables cover colors, fonts, message window size, choice layer spacing,
  viewport size, sprite placement, and transition duration

Suggested class groups:

```txt
tzr-html-player
tzr-html-viewport
tzr-html-title
tzr-html-stage
tzr-html-visual-layer
tzr-html-audio-layer
tzr-html-message-window
tzr-html-choice-layer
tzr-html-status
tzr-html-error
```

Do not design a full theme system in the first implementation.

## examples/html-basic Structure

Planned files:

```txt
examples/html-basic/
  README.md
  package.json
  assets.ts
  index.html
  vite.config.ts
  tsconfig.json
  tsuzuru.config.ts
  scenario/
    main.tzr
    chapters/
      01-opening.tzr
  src/
    main.ts
    style.css
    screens/
      settings.html
  public/
    assets/
      images/
      audio/
```

`package.json` should depend on:

- `@tsuzuru/html`
- `@tsuzuru/config`
- `@tsuzuru/plugin-std-visual`
- `@tsuzuru/plugin-std-audio`

and use `@tsuzuru/cli`, TypeScript, Vite, and Vitest as needed for development.
It should not depend on Preact.

`src/main.ts` should be intentionally small and use the declarative app API:

```ts
import "@tsuzuru/html/style.css";
import { mountTsuzuruHtmlAppsFromDocument, normalizeTsuzuruHtmlAssetsManifest } from "@tsuzuru/html";
import { assets as assetsManifest } from "../assets.js";
import settingsHtml from "./screens/settings.html?raw";
import "./style.css";

const assets = normalizeTsuzuruHtmlAssetsManifest(assetsManifest, new URL("../assets.ts", import.meta.url));

await mountTsuzuruHtmlAppsFromDocument(document, {
  assets,
  screenFragments: {
    settings: settingsHtml,
  },
});
```

`tsuzuru.config.ts` should validate the same source files:

```ts
import { defineTsuzuruConfig } from "@tsuzuru/config";
import { createStdAudioPlugin } from "@tsuzuru/plugin-std-audio";
import { createStdVisualPlugin } from "@tsuzuru/plugin-std-visual";

export default defineTsuzuruConfig({
  scenario: {
    entry: "scenario/main.tzr",
    files: ["scenario/**/*.tzr"],
  },
  plugins: [createStdVisualPlugin(), createStdAudioPlugin()],
});
```

The example should include a Playwright smoke test only if the package-level UI
surface needs browser verification in the same implementation goal. Otherwise,
start with `check:scenario`, `build`, and a focused package test suite.

## Open Questions

- Should `mountTsuzuruHtml` always render a title screen, or should title screen
  rendering be controlled by an option after the first implementation?
- Should the first HTML package include text reveal and auto mode UI, or keep
  those in later package helpers?
- Should `assets.json` support multiple candidate `src` values per audio/image
  asset for browser format fallback?
- Should URL scenario loading allow cross-origin includes, or keep includes
  same-origin by default?
- Should a future manifest list scenario documents explicitly for hosts that do
  not want recursive include fetches?
