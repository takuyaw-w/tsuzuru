# v1.0 Manual Publish Checklist

## Purpose

This checklist defines the manual release execution path for Tsuzuru v1.0. It
separates readiness review from actual release execution and records the order
for versioning, package publishing, tag creation, GitHub release notes, and
post-publish smoke checks.

This document is not release approval. A maintainer must still make the final
release decision from a clean `main` checkout.

## Non-goals / Safety

Do not run these commands during readiness review:

```sh
pnpm release:version
npm publish
pnpm publish
git tag
git push
git push --tags
gh release create
```

Do not publish from direct package paths such as `npm publish ./packages/core`.
Use workspace-aware `pnpm --filter <package> publish` during actual release
execution so workspace protocol dependencies are converted to publishable
semver ranges.

This checklist does not implement npm provenance, trusted publishing, release
automation, rollback automation, or a package migration framework.

## Preconditions

- The release is cut from `main`.
- The working tree is clean.
- The target version and release type are decided.
- All public packages intended for v1.0 are included in the publish inventory.
- The release owner has npm access to the `@tsuzuru` organization and the
  unscoped `create-tsuzuru` package.
- The release owner has GitHub permission to push the version commit / tag and
  create the GitHub release.
- No release command is run from an unreviewed local checkout.

## Required Local Gates

Run these from a clean checkout before actual release execution:

```sh
pnpm inventory:check
pnpm format:check
pnpm lint
pnpm check
pnpm test
pnpm typecheck
pnpm packages:build
pnpm publish-readiness:check
pnpm release-readiness:check
git diff --check
```

`publish-readiness:check` assumes package `dist` output already exists. On a
clean checkout, run `pnpm packages:build` first or use
`pnpm release-readiness:check`.

## Optional Gates

Optional confidence checks:

```sh
pnpm examples:e2e
pnpm packages:graph:check
```

`examples:e2e` remains an optional browser smoke gate. `packages:graph:check`
is optional / manual dependency graph validation and is not a v1.0 required
gate.

## NPM Account / Organization Checks

Before actual publish, verify:

- `npm whoami` returns the intended release account.
- the release account has owner or publish permission for the `@tsuzuru` npm
  organization.
- the release account can publish the unscoped `create-tsuzuru` package.
- package names and access settings are correct.
- scoped packages publish publicly.

All scoped packages currently declare:

```json
{
  "publishConfig": {
    "access": "public"
  }
}
```

`create-tsuzuru` is unscoped and does not require `publishConfig.access`.

## Provenance / 2FA Decision

Make these decisions before actual publish:

- whether v1.0 uses npm provenance
- whether manual local publish is acceptable for v1.0
- whether GitHub Actions trusted publishing is in scope
- whether npm two-factor authentication mode changes the publish procedure
- whether publish commands need OTP handling

Do not invent npm policy in this repo. If current npm provenance or 2FA
behavior matters for the release, verify it against npm documentation and the
active npm account immediately before actual publish.

## Version Bump Procedure

For v1.0, keep the root package, all public packages, and private example
packages version-synchronized to the chosen release version. The root package
is private, but its version is used as the repository release marker. Examples
are private and not publish targets, but their versions remain synchronized so
example package metadata tracks the same repo release as the runtime packages.

The current repository has one independent patch difference:

- most public packages are `0.1.1`
- `create-tsuzuru` is `0.1.2`

The v1.0 version bump should bring these to the same chosen release version.

Current `pnpm release:version <version>` behavior:

- checks the current branch is `main`
- fetches and pulls from origin
- requires a clean working tree
- edits selected package versions
- runs `rtk pnpm test`
- runs `rtk pnpm typecheck`
- commits the version change
- creates an annotated `v<version>` tag
- pushes `main`
- pushes the tag

Do not run `pnpm release:version` during readiness review.

The current script target list is aligned with the v1.0 inventory: root
`package.json`, every public package under `packages/*`, and every private
example package under `examples/*`. `pnpm inventory:check` fails if that target
list drifts from the current public package or example inventory.

Before using `release:version` for v1.0, still review the generated diff and
confirm maintainers intend to run the script. It remains an actual release
execution script because it commits, creates an annotated tag, and pushes.

## Release Notes Procedure

Prepare release notes before publishing packages. The release notes should
include:

- version
- release date
- package list
- user-facing highlights
- breaking changes
- migration notes
- known limitations
- verification summary
- links to the release gate docs
- post-publish smoke result after it is available

Recommended location:

[`docs/releases/v1.0.0.md`](../releases/v1.0.0.md)

The current file is a draft until actual release execution fills in the release
date, final verification results, and post-publish smoke result.

Create the GitHub release notes from the reviewed release notes document.

## Tag / GitHub Release Procedure

For actual release execution only:

1. Create the version bump commit after final gates pass.
2. Create an annotated tag named `v<version>`, for example `v1.0.0`.
3. Push the version bump commit and tag only when the package publish plan is
   approved.
4. Create the GitHub release from the tag and reviewed release notes.

Do not create tags or GitHub releases from readiness review.

If package publish fails after a tag is pushed, do not rewrite public history
without a separate maintainer decision. Prefer documenting the failure and
publishing a corrective version if needed.

## Publish Order

Publish in dependency order:

1. `@tsuzuru/core`
2. `@tsuzuru/config`
3. `@tsuzuru/standard-game-storage`
4. `@tsuzuru/vite-plugin`
5. `@tsuzuru/plugin-std-visual`
6. `@tsuzuru/plugin-std-audio`
7. `@tsuzuru/plugin-std-text-sound`
8. `@tsuzuru/plugin-std-effect`
9. `@tsuzuru/plugin-std-camera`
10. `@tsuzuru/plugin-std-particle`
11. `@tsuzuru/plugin-std-system`
12. `@tsuzuru/preact`
13. `@tsuzuru/standard-ui-preact`
14. `@tsuzuru/cli`
15. `create-tsuzuru`

Rationale:

- core has no internal dependencies and is the foundation for adapters and
  plugins.
- config has no internal dependencies and is required by CLI and standard game
  storage.
- standard game storage depends on config and core, and generated templates can
  depend on it.
- vite-plugin depends on core and is used by generated templates and examples.
- standard plugins, Preact, and standard UI depend on core.
- CLI depends on core and config.
- `create-tsuzuru` publishes last because generated templates depend on
  already-published `@tsuzuru/*` packages.

## Publish Dry-run / Pack Review

Run pack review before publish:

```sh
pnpm packages:build
pnpm run pack:dry-run
pnpm publish-readiness:check
```

For publish-time workspace protocol conversion, use `pnpm publish --dry-run`
per package during release execution planning. These dry-runs are not part of
normal readiness review unless explicitly approved for the release.

Actual release dry-run command shape:

```sh
pnpm --filter @tsuzuru/core publish --dry-run
pnpm --filter @tsuzuru/config publish --dry-run
pnpm --filter @tsuzuru/plugin-std-visual publish --dry-run
pnpm --filter @tsuzuru/plugin-std-audio publish --dry-run
pnpm --filter @tsuzuru/plugin-std-text-sound publish --dry-run
pnpm --filter @tsuzuru/plugin-std-effect publish --dry-run

pnpm --filter @tsuzuru/cli publish --dry-run
pnpm --filter create-tsuzuru publish --dry-run
```

## Post-publish Verification

After all packages are published, run the registry smoke:

```sh
pnpm run smoke:create-tsuzuru:registry
```

This verifies that published `create-tsuzuru` can create a project that
installs from the registry, validates its scenario, and builds.

Optional additional registry check:

```sh
TSUZURU_SMOKE_CREATE_PM=npm pnpm run smoke:create-tsuzuru:registry
```

Record the smoke result in the release notes and GitHub release.

## Rollback / Failure Handling

If a pre-publish gate fails, stop and fix the repository before publishing.

If a package publish fails before all packages are published:

- stop publishing immediately
- record which packages were published
- decide whether retrying the same version is valid for the failed package
- avoid deleting or unpublishing packages without a maintainer decision
- prefer a corrective patch version if a broken package was already published

If post-publish smoke fails:

- keep the generated smoke temp directory when possible for inspection
- record the failure in the release notes or issue tracker
- decide whether a corrective release is required

## Do Not Run During Readiness Review

Readiness review may run local checks and inspect docs/scripts. It must not run:

```sh
pnpm release:version
npm publish
pnpm publish
git tag
git push
git push --tags
gh release create
```

It also must not edit package versions, create release commits, change npm
dist-tags, or create GitHub releases.
